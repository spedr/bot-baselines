# Lee et al. 2011 (content-polluter random forest) — implementation spec

Method id: `lee2011`. Family: feature-based (profile + tweet-content features), random forest.
Graph: no. Text: yes (tweet texts only, regex + static word vectors + zlib). Temporal: no (account age only).
GPU: none.

## 1. Summary

Lee, Eoff and Caverlee (ICWSM 2011) collected "content polluters" with social honeypots and trained
Weka classifiers on 19 hand-crafted account features in four groups (user demographics, friendship
network, content, history). Random forest was best (98.42% accuracy, F1 0.984, 10-fold CV on their own
honeypot data). The TwiBot-22 benchmark re-implementation (`src/Lee`) keeps 14 of the 19 features
(8 profile features + 6 content features computed from up to 20 tweets on TwiBot-22, up to 200 on
the other datasets) and trains `RandomForestClassifier(n_estimators=76)`. The friendship-overlap,
following/follower ID standard deviations and following change rate are dropped because the
datasets lack the required data. We re-implement the benchmark version (the published numbers come
from it), with an optional switch for the paper's screen-name length definition.

## 3. Inputs

### 3.1 Feature vector (benchmark, 14 columns, in this order)

Column order matters only for RF randomness, but keep it. Source: `user_feature_extraction.py`
L10-21 and `Twibot-22/content_feature_extraction.py` L11-23 **[P-code]**.

| # | Column (benchmark name) | Definition in benchmark code | Paper definition |
|---|---|---|---|
| 0 | `screen_name_length` | `len(user['name'])`, i.e. the DISPLAY NAME, not the screen name; 0 if null (`user_features.py` L36-41) | length of the screen name |
| 1 | `description_length` | `len(description)`, 0 if null; no strip | same |
| 2 | `account_longvity` | days from `created_at` date (time dropped) to a fixed collection date: TwiBot-22 2022-04-20; all others 2020-10-01 (`user_features.py` L10-33). 0 if `created_at` null or ends with `L` | longevity of the account |
| 3 | `following_count` | `public_metrics.following_count` (int, null→0) | number of following |
| 4 | `followers_count` | `public_metrics.followers_count` (null→0) | number of followers |
| 5 | `following_to_followers` | following / followers; 0.0 if followers == 0 or either null | ratio of following and followers |
| 6 | `tweets_count` | `public_metrics.tweet_count` (null→0) | number of posted tweets |
| 7 | `tweets_count_per_day` | tweets_count / longevity; if longevity == 0 returns tweets_count | posted tweets per day |
| 8 | `links_ratio` | (#URL regex matches over all selected tweets) / #tweets | \|links\| / \|tweets\| |
| 9 | `unique_links_ratio` | (#distinct URL strings over all selected tweets) / #tweets | \|unique links\| / \|tweets\| |
| 10 | `mention_ratio` | (#mention regex matches) / #tweets | \|@username\| / \|tweets\| |
| 11 | `unique_mention_ratio` | (#distinct mention strings) / #tweets | \|unique @username\| / \|tweets\| |
| 12 | `compression_ratio` | uncompressed bytes / ZIP file bytes (see 3.3) | uncompressed / compressed size of tweets |
| 13 | `similarity` | mean pairwise spaCy `Doc.similarity` over all unordered tweet pairs; 1 if a single tweet (see 3.4) | average content similarity over all pairs (similarity function not specified) |

Dropped vs paper (5 of 19; readme L41) **[P-code]**: two bidirectional-friend percentages
(|following ∩ followers| / |following| and / |followers|), std of following IDs, std of follower IDs,
following change rate (needs hourly profile history). Note: the benchmark paper's appendix says
"18 features"; the code uses 14 **[P-paper vs P-code]**.

Regexes (`content_features.py` L6-25), copy exactly, Python `re`, case-sensitive:
- URL: `http[s]?://(?:[a-zA-Z]|[0-9]|[$-_@.&+]|[!*\(\),]|(?:%[0-9a-fA-F][0-9a-fA-F]))+`
  (`[$-_]` is the character RANGE 0x24-0x5F; it matches `:/?=#` digits and upper case; keep it).
- Mention: `@(?:[a-zA-Z]|[0-9]|[_+])+`.
Unique counts are over the union of all selected tweets of the user (Python `set` of matched strings).

### 3.2 Which tweets

- Benchmark: tweet ids come from `edge.csv` rows with `relation == 'post'` (user → tweet), grouped by
  user after `df.sort_values(by="source_id")` (pandas default quicksort, NOT stable), then
  `post[:20]` on TwiBot-22 and `post[:200]` on TwiBot-20 / Cresci (`content_feature_extraction.py`
  L25-28). The within-user order is therefore effectively arbitrary, not "latest" (readme L38 says
  "top 20 ... not the latest") **[P-code]**.
- TwiBot-20: users have at most 200 tweets, so `[:200]` means ALL of the user's tweets.
- Ours: take tweets from the shared tweets store (newest first, cap 200). TwiBot-22: first 20
  (newest 20). TwiBot-20 / Cresci: all (≤200). Config `lee.tweets_per_user` (default 20 for
  TwiBot-22, 200 otherwise) and `lee.tweet_order: newest|random` (`random` = seeded shuffle of the
  stored ≤200 before truncation, closer in spirit to the benchmark's arbitrary order). Deviation **[U]**
  impact; ablate on TwiBot-22.
- Only the tweet TEXT is used. No per-tweet metadata (retweet flag, entities, timestamps) is needed:
  URLs and mentions are regex-matched on the raw text (retweets keep their `RT @user:` prefix, which
  counts as a mention). The processed per-user jsonl texts suffice.

### 3.3 Compression ratio (exact)

Benchmark `zip_ratio` (`content_features.py` L46-61): writes `"\n".join(texts) + "\n"` (each text then
`\n`) to `./temp_tweets.txt` in text mode (UTF-8 on Linux), `unzip_size = os.path.getsize`, then
`zipfile.ZipFile('./temp_tweets.txt.zip','w', ZIP_DEFLATED).write('./temp_tweets.txt')` and reads
the ZIP size WITHOUT closing the archive. Under CPython's `zipfile`, at that moment the file holds the
local header (30 B + 15 B arcname `temp_tweets.txt`) plus the raw-deflate stream (the header rewrite
seeks, which flushes); the central directory is only written when the object is garbage-collected
after the size was read **[P-code + reading of CPython zipfile; U for exact flush behaviour]**.
Implement in memory, no temp files:

```
U = len(("\n".join(texts) + "\n").encode("utf-8"))
c = zlib.compressobj(level=-1 /* =6 */, method=zlib.DEFLATED, wbits=-15)
C = len(c.compress(bytes) + c.flush())
compression_ratio = U / (C + zip_overhead)     # zip_overhead default 45
```

Config `lee.zip_overhead_bytes` (45 faithful; 0 = "pure" ratio as in the paper). The temp-file race in
the benchmark (fixed path) is a non-issue for a single process; ours is in memory and parallel-safe.

### 3.4 Similarity (exact)

Benchmark: `nlp = spacy.load('en_core_web_lg', disable=['parser','ner'])`; each tweet → `nlp(text)`;
mean of `doc_i.similarity(doc_j)` over all i<j; returns 1 if exactly one tweet. spaCy v3
`Doc.similarity` semantics **[P-code spaCy v3, U for the exact spaCy/model version the benchmark used]**:
1. if both docs have the same length and identical token `orth` sequence → 1.0;
2. doc vector = mean over ALL tokens of `token.vector` (zeros for tokens without a vector);
3. if either doc vector has norm 0 → 0.0;
4. else cosine of the two doc vectors.

Our implementation: tokenizer only (`spacy.load("en_core_web_lg", exclude=[all pipes])`; the
tagger/lemmatizer do not affect vectors), look up each token's vector by exact `orth` in the model's
vector table, sum (scale does not change cosine), L2-normalise, compute the Gram matrix
`V V^T` (n ≤ 200), override entries for identical token sequences with 1.0 and for zero-norm rows
with 0.0, average the strict upper triangle. Pin `spacy==3.7.*` and `en_core_web_lg==3.7.*`
(300-d, ~514k vectors) **[U: benchmark versions unknown]**.

### 3.5 Users included (benchmark quirk)

`user_feature_extraction.py` L79-83 keeps only users present in `user_to_post.csv`, i.e. labelled
users with at least one `post` edge. Users with zero tweets are DROPPED from train, val AND test
(also needed because `count_urls` divides by #tweets) **[P-code]**. So the benchmark's Lee test set is
smaller than 100k on TwiBot-22 (count unknown **[U]**). Ours: `lee.zero_tweet_policy: drop|fill`
(default `drop` for parity; log how many test users were dropped). `fill`: content columns = NaN
→ sentinel -1, so all test users are scored; report both.

### 3.6 What we need from the shared layer

- `users.parquet`: `idx, user_id, split, label` (labelled users only; support users unused).
- `profile.parquet`: `name` (display name), `screen_name` (only for the paper-variant column 0),
  `description`, `created_at` (parsed UTC timestamp), `followers_count`, `following_count`,
  `statuses_count`. TwiBot-20 raw strings carry trailing spaces ("SHAQ ", "None ") and string
  counts; the layer must strip, map "None" → null, cast counts to int **[P: raw file inspected]**.
- tweets store: per-user texts, newest first, cap 200 (offsets + text). No metadata.
- spaCy `en_core_web_lg` vector table (export once to `artifacts/models/en_core_web_lg/vectors.f32.npy`
  [514k, 300] + `orth→row` mapping) — not in the shared layer; method-local asset.
- Collection dates (constants, benchmark): TwiBot-22 2022-04-20, everything else 2020-10-01 (also
  Cresci, which is wrong in spirit but is what the code does). Config `lee.reference_date`.

## 4. Architecture

`sklearn.ensemble.RandomForestClassifier(n_estimators=76)`, all other parameters default
(`criterion='gini'`, `max_depth=None`, `min_samples_leaf=1`, `max_features='sqrt'` → int(sqrt(14)) = 3,
`bootstrap=True`, `class_weight=None`) (`train.py` L35) **[P-code]**. n_estimators=76 was "tuned on the
validation set" (readme L40); no other tuning. No feature scaling. Hard `predict` (threshold 0.5 on
the vote fraction). We additionally store `predict_proba` for AUC / macro-F1 extras.

## 5. Training

- Train on `split == train` rows only; val unused (note: `train.py` filters `'valid'`, but TwiBot-22's
  `split.csv` says `val`, so the benchmark's val frame is empty; harmless) **[P-code; split.csv inspected]**.
- Test on `split == test`. No early stopping.
- Seeds: benchmark is unseeded (no `random_state`), five runs. Ours: `random_state ∈ {0,1,2,3,4}`,
  `n_jobs=8` (identical results to n_jobs=1 for a given seed).
- TwiBot-20 split: official 8,278 / 2,365 / 1,183 (minus zero-tweet users under `drop`).

## 7. Scale plan

Memory rule (mandatory): every job runs through `tools/memrun` (MemoryMax 10G, no swap, serialised by
lock); design target peak RSS ≤ 8 GB; never load a full TwiBot-22 tweet file, edge file or full
feature table into RAM; stream / chunk / memmap.

| Step | TwiBot-22 work | Peak host RSS (arithmetic) | VRAM | Wall-clock |
|---|---|---|---|---|
| 0. Export spaCy vectors once | 514k × 300 × 4 B = 617 MB `.npy` + orth map (~40 MB) | spaCy load ~1.5 GB | 0 | 2 min |
| 1. Profile features | 1M rows × 8 cols × 8 B = 64 MB | < 0.5 GB | 0 | < 1 min |
| 2. Content features | ≤ 20 tweets × 1M users ≈ ≤ 20M texts, read via store offsets in chunks of 50k users (≈1M texts × ~150 B ≈ 150 MB per chunk) | parent: vectors memmap 0.6 GB (page cache, shared) + chunk 0.3 GB; 6 forked workers × (tokenizer/vocab ~0.4 GB + chunk 0.1 GB) ≈ 3 GB → total ≈ 4 GB | 0 | tokenizer ~20-40k tweets/s/core [U] → 20M / (6 × 25k) ≈ 2-3 min CPU, store I/O (~3 GB of text at ~70 MB/s if on the slow drive) ≈ 1 min; zlib and 20×20 Gram negligible. Budget 15-30 min |
| 3. RF train (per seed) | X_train 700k × 14 × 4 B (float32) = 39 MB | trees: ~2 × leaves nodes; with noisy labels ~150k leaves/tree [U] → 300k nodes × ~80 B = 24 MB/tree × 76 = 1.8 GB; + data/indices < 0.2 GB → ≈ 2.5 GB | 0 | n_jobs=8: 1-3 min |
| 4. Predict/eval | 100k × 14 | model 1.8 GB + 0.1 GB | 0 | < 1 min |

TwiBot-20: 11,826 labelled users × ≤ 200 tweets ≈ 2.4M texts; Gram 200×200 per user trivial;
≈ 5 min total, < 2 GB. Total for the 5-seed run on both datasets: ≈ 1 CPU-hour, 0 GPU-hours.
Do not keep a fitted forest in memory across seeds (fit → predict → delete).

## 8. ExtScore column

- Flag `extscore: none | p` (default `none` reproduces the baseline exactly: 14 columns, same order).
- `extscore: p`: append two columns AFTER column 13: `extscore_p` = p with missing → -1.0, `extscore_missing` ∈ {0,1}
  (shared tree transform). Width 14 → 16; `max_features='sqrt'` then gives int(sqrt(16)) = 4 instead
  of 3. Default: let it change (report it); ablation `lee.max_features=3` keeps the baseline's
  per-split feature count so any gain is not a capacity artefact.
- Alternative: NaN-native (sklearn ≥ 1.4 RandomForest supports NaN) with only `extscore_p` (no indicator);
  ablate.
- Late-fusion ablation: logistic regression on `[logit(rf_proba_oob or val), z, m]` fitted on the
  val split (RF trained on train only), evaluated on test.
- Reference rows: ExtScore alone (p ≥ 0.5) on the same test users.
- ExtScore must be present on a representative fraction of TRAIN rows; if ExtScore was only computed for test
  users the RF cannot learn to use it (all-missing in training) → only the late-fusion variant is valid.
  Log ExtScore coverage per split. Support/unlabelled users are not used by this method.
- Report MDI and permutation importance (on val) of `extscore_p`.

## 9. Pitfalls

1. Column 0 is the display-name length (`user['name']`), labelled `screen_name_length`. Faithful
   default = display name; `lee.col0: name|screen_name` (paper says screen name).
2. Zero-tweet users are silently dropped from the test set in the benchmark (3.5). Compare like with
   like; never report a `drop` number next to a full-test number without saying so.
3. The ZIP "compressed size" includes 45 bytes of header in the faithful mode (3.3).
4. Two different fixed collection dates (2022-04-20 TwiBot-22; 2020-10-01 everything else) and date-only
   arithmetic. Lee's longevity ≠ BotHunter/SGBot's (Dec 31 of the dataset year).
5. TwiBot-22 `tweet_split.py` as published cannot work: `df.append(...)` result is discarded (L21), so
   the per-file frames are empty. The published numbers must come from an unpublished working variant
   **[P-code]**; another reason to treat tweet selection as uncertain.
6. spaCy similarity is O(n²) per user if done with `Doc.similarity` loops (19,900 pairs × 11,826
   TwiBot-20 users); use the vectorised Gram matrix with the identical-token override.
7. TwiBot-20 raw profile values are strings with a trailing space. `len(des)` and `len(name)` in the
   benchmark do not strip, and we do not hold the benchmark's converted TwiBot-20 `node.json`, so we
   cannot tell whether its strings kept the space (+1 to every length; RF-invariant except for empty
   strings). Default: compute on the stripped string **[U]**.
8. No label leakage: no transductive features; tweets are the user's own.

## 11. Acceptance check

Faithful mode (`extscore: none`, `zero_tweet_policy: drop`, display-name column, overhead 45), 5 seeds:
- TwiBot-20 (official split): accuracy 77.4 ± 1.5, bot F1 80.0 ± 1.5.
- TwiBot-22 (official split): accuracy 76.3 ± 1.0, bot F1 30.4 ± 3.0 (wider: tweet selection differs).
- Cresci-2015 / 2017 on our own hash split: accuracy ≥ 96 (not the benchmark split; sanity only).
If TwiBot-22 F1 misses by more than 3 points, rerun with `tweet_order: random` before debugging further.
